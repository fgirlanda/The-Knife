# Spiegazione delle modifiche al database

## Obiettivo della modifica

Il progetto The Knife inizialmente salvava e caricava i dati attraverso file
CSV. La nuova architettura utilizza PostgreSQL come sistema di persistenza.

Lo scopo delle modifiche effettuate è stato preparare il livello di accesso ai
dati tramite classi DAO (Data Access Object), mantenendo il più possibile lo
stesso comportamento che il programma aveva con i CSV.

Al momento i DAO sono pronti e funzionanti, ma i controller utilizzano ancora
le classi CSV. La sostituzione nei controller dovrà essere effettuata in un
passaggio successivo.

## Struttura PostgreSQL rilevata

Il database `TheKnife` contiene quattro tabelle:

- `utenti`;
- `ristoranti`;
- `recensioni`;
- `preferiti`.

Le relazioni principali sono:

- `ristoranti.proprietario` fa riferimento a `utenti.id_utente`;
- `recensioni.id_cliente` fa riferimento a `utenti.id_utente`;
- `recensioni.id_ristorante` fa riferimento a
  `ristoranti.id_ristorante`;
- `preferiti.id_cliente` fa riferimento a `utenti.id_utente`;
- `preferiti.id_ristorante` fa riferimento a
  `ristoranti.id_ristorante`.

La chiave primaria di `preferiti` è composta dalla coppia
`(id_cliente, id_ristorante)`. Questo impedisce di inserire due volte lo stesso
ristorante tra i preferiti del medesimo cliente.

## Modifiche effettuate direttamente sul database

### ID autoincrementale delle recensioni

La colonna `recensioni.id_recensione` era una chiave primaria intera, ma non
generava automaticamente il proprio valore.

È stata convertita in:

```sql
GENERATED BY DEFAULT AS IDENTITY
```

PostgreSQL ha quindi creato la sequence:

```text
recensioni_id_recensione_seq
```

Ora, quando viene inserita una recensione, non bisogna calcolare o specificare
manualmente il suo ID. L'inserimento può omettere `id_recensione` e recuperare
il valore generato con:

```sql
RETURNING id_recensione
```

Anche `utenti.id_utente` e `ristoranti.id_ristorante` sono colonne identity e
vengono gestite nello stesso modo dai rispettivi DAO.

### Username univoco

Prima di applicare la modifica è stato verificato che non esistessero username
duplicati. Successivamente è stato aggiunto questo vincolo:

```sql
ALTER TABLE utenti
ADD CONSTRAINT utenti_username_unique UNIQUE (username);
```

PostgreSQL ora impedisce in modo definitivo la registrazione di due utenti con
lo stesso username.

Il controllo applicativo tramite `UtenteDAO.esisteUsername()` rimane utile per
mostrare immediatamente un messaggio comprensibile all'utente. Il vincolo nel
database, però, è la garanzia effettiva contro i duplicati, anche in presenza di
due registrazioni contemporanee.

Se l'inserimento viola il vincolo sullo username, `UtenteDAO` genera
`UsernameGiaEsistenteException` con il messaggio "Username già in uso". I dati
nulli o non validi passati ai DAO vengono invece segnalati in modo uniforme con
`IllegalArgumentException`.

### Una recensione per cliente e ristorante

È stato aggiunto il vincolo:

```sql
ALTER TABLE recensioni
ADD CONSTRAINT recensioni_cliente_ristorante_unique
UNIQUE (id_cliente, id_ristorante);
```

La chiave primaria `id_recensione` continua a identificare la singola
recensione. Il nuovo vincolo impedisce invece che lo stesso cliente inserisca
più recensioni per lo stesso ristorante, anche quando due richieste concorrenti
arrivano nello stesso momento.

## Come funzionava prima con i CSV

Il programma utilizzava queste classi:

- `UtenteCSV` per `utenti.csv`;
- `RistoranteCSV` per `ristoranti.csv`;
- `RecensioneCSV` per `recensioni.csv`;
- `PreferitiCSV` per `preferiti.csv`.

La classe astratta `GestoreCSV` forniva le operazioni generali per:

- caricare tutte le righe di un file;
- aggiungere una nuova riga;
- riscrivere completamente un file;
- rimuovere una riga;
- ricavare il successivo ID contando le righe presenti.

### Caricamento

Con i CSV era normalmente necessario leggere l'intero file:

```java
List<Ristorante> ristoranti = ristoranteCSV.caricaCSV();
```

I filtri venivano applicati successivamente in Java. Per esempio, il profilo
del ristoratore caricava tutti i ristoranti e poi manteneva soltanto quelli il
cui proprietario corrispondeva all'utente autenticato.

### Mappe in memoria

`UtenteCSV` e `RistoranteCSV` costruivano mappe statiche per effettuare ricerche
rapide:

```text
username -> Utente
idRistorante -> Ristorante
```

Le mappe dovevano essere popolate dopo il caricamento dei CSV e aggiornate
manualmente quando veniva aggiunto un nuovo oggetto.

### Collegamento tra ristoranti e recensioni

`RistoranteCSV` caricava prima tutte le recensioni da `recensioni.csv`, le
raggruppava per ID del ristorante e successivamente leggeva `ristoranti.csv`.

Per ogni ristorante venivano aggiunte le recensioni corrispondenti:

```java
ristorante.aggiungiRecensione(recensione);
recensione.setRistorante(ristorante);
```

La chiamata `aggiungiRecensione()` aggiornava anche la media delle recensioni.

### Generazione degli ID

Gli ID dei nuovi elementi venivano ricavati contando le righe del CSV tramite
`ultimoID()`. Questo sistema poteva diventare inaffidabile in seguito a
cancellazioni o scritture contemporanee.

### Modifiche e cancellazioni

Per modificare o rimuovere una recensione era necessario:

1. leggere tutto il file;
2. modificare o escludere la riga interessata;
3. riscrivere completamente il CSV.

Anche i preferiti venivano controllati scorrendo tutte le righe del relativo
file.

## Come funzionerà con i DAO

Le nuove classi si trovano nel package `com.gruppo10.database`:

- `UtenteDAO`;
- `RistoranteDAO`;
- `RecensioneDAO`;
- `PreferitoDAO`.

Ogni DAO si occupa esclusivamente della lettura e della modifica della propria
tabella PostgreSQL. Le query usano `PreparedStatement`, quindi i valori vengono
separati dal testo SQL e gestiti correttamente anche quando contengono caratteri
speciali.

Connessioni, statement e risultati vengono chiusi automaticamente tramite
`try-with-resources`.

## UtenteDAO

`UtenteDAO` mette a disposizione operazioni per:

- caricare tutti gli utenti;
- cercare un utente tramite ID;
- cercare un utente tramite username;
- controllare se uno username esiste;
- inserire un nuovo utente.

L'inserimento non utilizza più `ultimoID()`. PostgreSQL genera l'ID e il DAO lo
assegna all'oggetto Java:

```sql
INSERT INTO utenti (...)
VALUES (...)
RETURNING id_utente;
```

Il DAO valida anche la presenza dei campi obbligatori e impedisce di salvare
come utente persistente un oggetto con ruolo `NON_REGISTRATO`.

## RistoranteDAO

`RistoranteDAO` mette a disposizione operazioni per:

- caricare tutti i ristoranti;
- cercare un ristorante tramite ID;
- cercare i ristoranti applicando i filtri direttamente nel database;
- caricare direttamente i ristoranti di uno specifico proprietario;
- caricare direttamente i ristoranti preferiti di un cliente;
- inserire un nuovo ristorante.

Il metodo `cercaConFiltri()` crea una nuova query a ogni ricerca. Nome, cucina,
prezzo, media delle recensioni, delivery, prenotazione e distanza vengono
trasformati in condizioni SQL soltanto quando il relativo filtro è attivo. I
valori `TUTTO` non aggiungono condizioni.

La ricerca per nome non distingue maiuscole e minuscole. Il prezzo mantiene il
comportamento della pagina principale ed è interpretato come soglia massima; la
media è invece una soglia minima. La distanza viene calcolata da PostgreSQL con
le coordinate geografiche e la formula della distanza sulla superficie
terrestre.

Il DAO restituisce una nuova `List<Ristorante>` con i risultati aggiornati del
database. Il controller dovrà quindi raccogliere le selezioni della GUI, chiamare
`cercaConFiltri()` e mostrare la lista ricevuta, invece di filtrare la lista
precedentemente caricata.

Il caricamento usa un `LEFT JOIN` tra `ristoranti` e `recensioni`. In questo
modo vengono restituiti anche i ristoranti che non hanno recensioni.

Poiché una query con join può produrre più righe per lo stesso ristorante, il
DAO utilizza temporaneamente una `LinkedHashMap<Integer, Ristorante>` per creare
un solo oggetto `Ristorante` e aggiungergli tutte le recensioni associate.

Per ogni recensione vengono impostati entrambi i collegamenti:

```java
recensione.setRistorante(ristorante);
ristorante.aggiungiRecensione(recensione);
```

In questo modo viene mantenuto il comportamento precedente e viene ricalcolata
anche la media delle recensioni.

L'inserimento utilizza l'identity PostgreSQL:

```sql
INSERT INTO ristoranti (...)
VALUES (...)
RETURNING id_ristorante;
```

Il DAO controlla inoltre che i valori `TUTTO`, utilizzati nelle caselle dei
filtri della GUI, non vengano salvati come caratteristiche reali di un
ristorante.

## RecensioneDAO

`RecensioneDAO` mette a disposizione operazioni per:

- caricare tutte le recensioni;
- cercare una recensione tramite ID;
- caricare le recensioni di un ristorante;
- caricare le recensioni scritte da un utente;
- caricare le recensioni dell'utente con il relativo ristorante completo;
- verificare se un cliente ha già recensito un ristorante;
- inserire una recensione;
- modificare testo e voto;
- aggiungere una risposta;
- rimuovere una recensione.

Modifiche e rimozioni ora vengono eseguite direttamente da PostgreSQL:

```sql
UPDATE recensioni ... WHERE id_recensione = ?;
DELETE FROM recensioni WHERE id_recensione = ?;
```

Non è più necessario riscrivere l'intero file. Il voto viene validato affinché
sia compreso tra 1 e 5.

Le risposte SQL `NULL` vengono convertite in stringhe vuote negli oggetti Java,
per mantenere la compatibilità con la GUI esistente.

Se un inserimento viola il vincolo sulla coppia cliente-ristorante, il DAO
genera `RecensioneDuplicataException` con il messaggio "Hai già recensito questo
ristorante". La futura integrazione con i controller o con il server potrà
intercettare questa eccezione e mostrare il messaggio all'utente.

Modifiche, risposte e cancellazioni richiedono sempre un `id_recensione` valido.
Non vengono più eseguiti aggiornamenti usando soltanto la coppia
cliente-ristorante.

Il metodo `trovaPerUtenteConRistorante()` è destinato al profilo cliente. Per
ogni recensione dell'utente restituisce anche il relativo oggetto `Ristorante`,
caricato con tutte le sue recensioni. In questo modo la card può mostrare il
nome del locale e aprirne la pagina senza dover effettuare una query per ogni
risultato.

Il metodo `RistoranteDAO.trovaPreferitiPerUtente()` usa un join con `preferiti`
e restituisce direttamente i ristoranti preferiti, evitando di caricare tutti i
ristoranti e controllarli uno alla volta nel controller.

## PreferitoDAO

`PreferitoDAO` mette a disposizione operazioni per:

- caricare tutti i preferiti;
- caricare i preferiti di un utente;
- verificare se una coppia utente-ristorante esiste;
- aggiungere un preferito;
- rimuovere un preferito.

L'aggiunta usa:

```sql
ON CONFLICT (id_cliente, id_ristorante) DO NOTHING
```

Se il preferito esiste già, PostgreSQL non crea un duplicato e l'operazione non
genera una seconda riga.

## Differenze principali tra CSV e PostgreSQL

| Prima, con i CSV | Ora, con PostgreSQL e DAO |
| --- | --- |
| Lettura dell'intero file | Query mirate ai dati necessari |
| Filtri eseguiti in Java | Filtri eseguibili direttamente con `WHERE` |
| ID calcolati contando le righe | ID generati dalle identity PostgreSQL |
| Mappe statiche da inizializzare | Ricerca diretta tramite query |
| File completamente riscritto per una modifica | `UPDATE` della sola riga interessata |
| Scansione completa per una cancellazione | `DELETE` con chiave primaria |
| Controlli applicativi sui duplicati | Vincoli `PRIMARY KEY` e `UNIQUE` nel database |
| Rischio di scritture concorrenti | Gestione della concorrenza affidata a PostgreSQL |

## Stato attuale del programma

I DAO sono stati compilati e verificati in lettura sul database PostgreSQL
locale. La verifica ha caricato correttamente utenti, ristoranti, recensioni e
preferiti senza modificare i dati.

I controller, tuttavia, importano e utilizzano ancora le classi CSV. Di
conseguenza, allo stato attuale il programma continua a usare i file CSV nei
normali flussi dell'interfaccia.

## Passaggio successivo consigliato

Il passo successivo sarà sostituire progressivamente nei controller:

```text
UtenteCSV      -> UtenteDAO
RistoranteCSV  -> RistoranteDAO
RecensioneCSV  -> RecensioneDAO
PreferitiCSV   -> PreferitoDAO
```

Durante la migrazione bisognerà:

1. gestire le `SQLException` nei controller;
2. eseguire prima l'operazione sul database e aggiornare la GUI solo dopo il
   successo;
3. eliminare la creazione delle mappe statiche non più necessarie;
4. usare query specifiche, come `trovaPerProprietario()`, invece di caricare e
   filtrare sempre tutti i dati;
5. verificare registrazione, login, ristoranti, recensioni e preferiti;
6. rimuovere le classi CSV soltanto quando non saranno più referenziate;
7. conservare eventualmente i CSV come backup o sorgente di importazione, non
   come archivio operativo principale.

## Configurazione della connessione

Attualmente URL, username e password PostgreSQL sono definiti direttamente in
`DatabaseConnection`. Prima della distribuzione sarebbe opportuno spostarli in
variabili d'ambiente o in un file di configurazione escluso dal versionamento,
evitando di salvare credenziali nel codice sorgente.
